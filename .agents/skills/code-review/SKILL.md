# Code Review Framework (ระบบตรวจทานโค้ดอัตโนมัติ)

> สกิลนี้ใช้ตรวจสอบความถูกต้องและคุณภาพของโค้ดที่เปลี่ยนแปลงบนกิ่งงาน (Branch) เปรียบเทียบกับกิ่งหลัก (`main` หรือ `master`)
> รองรับทุกเทคสแตกโดยปรับเปลี่ยนเกณฑ์การตรวจตามมาตรฐานที่ระบุไว้ใน Project SDD

---

## 2 โหมดการทำงาน (Review Modes)

| โหมด | ผู้เรียกใช้งาน | ช่วงเวลาที่ใช้ | เป้าหมาย |
|---|---|---|---|
| `pre-review` | AI (`dev-orchestrator`) | หลัง TDD ก่อนส่งถึงมนุษย์ | ตรวจหาและแก้ไขจุดบกพร่องที่ AI แก้ไขได้เอง เพื่อลดภาระการตรวจของคนให้น้อยที่สุด |
| `review` (ค่าเริ่มต้น) | มนุษย์ (Reviewer / Tech Lead) | ที่ ✋ Gate 7 | รายงานสรุปผลและข้อสังเกตเพื่อประกอบการตัดสินใจอนุมัติโค้ด |

---

## การจัดกลุ่มประเด็นในโหมด Pre-review (3 Groups)

เมื่อรันในโหมด `pre-review` ประเด็นทั้งหมดที่พบต้องถูกจัดเข้า 1 ใน 3 กลุ่มดังนี้:

1. **AI แก้ได้เลย:**
   - สิ่งที่แก้ได้ทันทีโดยไม่เปลี่ยนพฤติกรรมระบบ ไม่เปลี่ยนสเปค และไม่ต้องตัดสินใจด้านดีไซน์
   - ตัวอย่าง: โค้ดผิดระเบียบสถาปัตยกรรม, ตัวแปรไม่ได้ใช้งาน (Dead code), การละเมิด Linter, Hardcoded strings
   - **การดำเนินการ:** ส่งต่อให้ `implementer` แก้ไขทันที และรันเทสให้ผ่านทั้งหมด
2. **AI แก้ได้เลย · ต้องมีเทสก่อน:**
   - จุดที่ต้องเพิ่มหรือปรับพฤติกรรมตามที่ AC หรือสเปคระบุไว้แล้ว แต่โค้ดยังขาดไป
   - ตัวอย่าง: ลืมจัดการ Error Path ที่สเปคกำหนดไว้
   - **การดำเนินการ:** ส่งให้ `test-author` เขียน Automated Test ดักไว้ก่อน แล้วจึงให้ `implementer` แก้โค้ดให้ผ่าน
3. **ต้องให้คนตัดสิน:**
   - จุดที่กระทบกับสเปค, ต้องการการตัดสินใจทางสถาปัตยกรรม, หรือเป็นฟีเจอร์นอกเหนือจาก Story
   - **การดำเนินการ:** ห้าม AI แก้เองเด็ดขาด ให้รวบรวมไว้ในรายงานเพื่อส่งให้ Reviewer พิจารณาที่ ✋ Gate 7

## ขั้นตอนการตรวจสอบ (Review Procedure)

1. **อ่าน Project SDD และกติกาเฉพาะด้าน:** อ่าน `docs/sdd/` เพื่อนำเกณฑ์และ Checklist มาใช้
2. **ดึง Diff ของกิ่งงาน:**
   ```bash
   git diff origin/<base-branch>...HEAD
   ```
3. **รันคำสั่ง Linter / Static Analysis ประจำโปรเจกต์:** ตามที่ระบุใน SDD
4. **ตรวจสอบตาม 6 มิติหลัก:**
   - สถาปัตยกรรมและความถูกต้องของเลเยอร์ (Clean Architecture)
   - ความสอดคล้องกับสเปคและ AC (100% AC Coverage)
   - การจัดการข้อผิดพลาดและความปลอดภัย (Security & Error Handling)
   - ประสิทธิภาพและ Memory Leak
   - ความสะอาดของโค้ดและการตั้งชื่อ (Clean Code & Naming)
   - คุณภาพและความครอบคลุมของชุดการทดสอบ (Tests & Coverage)
5. **บันทึกรายงาน:**
   เขียนรายงานผลลงใน `docs/code-review/<ISSUE-KEY>-<mode>-r<round>.md`
