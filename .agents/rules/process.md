# กระบวนการพัฒนาซอฟต์แวร์ด้วย AI (AGY SDD Process & Methodology)

> เอกสารนี้คือ **Single Source of Truth (ความจริงแหล่งเดียว)** สำหรับลำดับขั้นตอนการทำงานใน AGY SDD
> AI ทุกตัว (Main Agent, Subagents, Skills) ต้องปฏิบัติตามลำดับขั้นตอนนี้อย่างเคร่งครัด
> หากมีคำสั่งหรือเอกสารใดขัดแย้งกับเอกสารนี้ → **ให้ยึดเอกสารนี้เป็นหลักเสมอ**

---

## ภาพรวมกระบวนการ (Overview of 2 Parts)

การพัฒนาในโปรเจกต์แบ่งออกเป็น 2 ส่วนหลัก:
1. **[Part 1] First-round SDD** — กำหนดมาตรฐานสถาปัตยกรรมทั้งโปรเจกต์ (ทำครั้งเดียวเมื่อเริ่มโปรเจกต์)
2. **[Part 2] Per Ticket Cycle** — ลูปพัฒนาทีละใบงาน ขับเคลื่อนด้วย `dev-orchestrator`

```text
[ก่อนเริ่ม Part 2] การเตรียม Backlog & GitHub Issues
   ├── 📝 สร้างการ์ดงาน / User Story + FR + AC ........... skill `create-task`
   ├── ✂️ แตกใบงานก้อนใหญ่เป็น Action Tasks [FE]/[BE] ..... skill `split-issue`
   └── 👤 มอบหมายงานให้คนรับผิดชอบ ...................... skill `assign-issues`
         │
         ▼

   ① Tech Lead สั่งเทคสแตกและสถาปัตยกรรมสั้น ๆ
   ② AI ขยายเป็นเอกสารมาตรฐานจริงใน `docs/sdd/` และ `AGENTS.md` ..... project-sdd-writer

[Part 2] ลูปต่อ 1 ใบงาน ................................. ขับเคลื่อนโดย dev-orchestrator
   A   แตกใบงานเป็น workspec รายฝั่ง (FE / BE) ............ workspec-writer + ผู้รับผิดชอบ
   B   ทำสเปคของใบงานนี้ให้เสร็จก่อนเขียนโค้ด ................. multi-agent
       ├── สำรวจโค้ดเดิมที่มี ............................. codebase-scout
       ├── สเปคหน้าจอและสถานะ (FE) ....................... spec-fe
       ├── สเปค API และข้อมูล (BE) ....................... spec-be
       ├── ⋈ จุดบรรจบ 1: เปรียบเทียบสัญญาสองฝั่ง .......... contract-checker
       └── วางแผนชุดเคสทดสอบ (🤖/👁️/🙋) ................. test-author
   ✋  Gate 6 — ตรวจอนุมัติสเปค & แผนการทดสอบ .............. Tech Lead
   C   TDD — เขียนเทสให้พังก่อน แล้วเขียนโค้ดให้ผ่าน ........ multi-agent

       ├── 2. เขียนโค้ดให้เทสผ่าน (ห้ามแก้ไฟล์เทส) .......... implementer

       └── 4. ตรวจความครบถ้วนของเทส & Coverage ............ test-reviewer
   ⋈   จุดบรรจบ 2: รวมโค้ดสองฝั่ง & รัน End-to-End ........ implementer

   D   QA — ตรวจสอบแยกเป็น 2 กองบน branch เดียวกัน ........ agent + มนุษย์
```

## บทบาทของคนในกระบวนการ (Human Roles)

| บทบาท | หน้าที่ในกระบวนการ |
|---|---|
| **BA / PO** | เขียนที่มาของ Story, Functional Requirements (FR) และ Acceptance Criteria (AC) — AI อ่านเท่านั้น ห้ามแก้ตามอำเภอใจ |
| **Tech Lead** | ตัดสินใจสถาปัตยกรรมใน Part 1, ตรวจอนุมัติ Gate 6 (สเปค) และดูแลความถูกต้องของระบบ |
| **Ticket Owner** | **คนหนึ่งคนรับผิดชอบใบงานตั้งแต่ต้นจนจบ** — ร่วมงานกับ AI ในทุกขั้น, ยืนยันการแบ่งฝั่ง, และทดสอบกองมนุษย์ |
| **Reviewer / Tech Lead** | ตรวจโค้ดที่ Gate 7 โดยเริ่มจากรายงานของ AI Pre-review และกดอนุมัติ |
| **ผู้มีสิทธิ์ Merge** | ตรวจดูความเรียบร้อยของ Pull Request ครั้งสุดท้ายบน GitHub แล้วกด Merge |
| **QA / Tester** | ทดสอบเคสในกองมนุษย์ 🙋 ที่ไม่สามารถรันอัตโนมัติได้ |

> ✋ = ประตูมนุษย์ (Human Gate) **AI ห้ามผ่านเอง ห้ามติ๊กเอง และห้ามสร้างบรรทัดอนุมัติเองเด็ดขาด**

## ขั้นตอนก่อน Part 2 — การจัดการ Backlog & GitHub Issues

### 1. การสร้างการ์ดงาน (skill `create-task`)
- **ผู้ใช้งาน:** PO, BA, Tech Lead หรือ Developer
- **หน้าที่:** แปลงไอเดียหรือชื่อฟีเจอร์ให้เป็น User Story มาตรฐาน
- **รูปแบบผลลัพธ์:**
  - **User Story:** ในฐานะ... / ฉันต้องการ... / เพื่อที่จะ...
  - **Functional Requirements:** รายการสิ่งที่ระบบต้องทำได้เป็น Checklist `- [ ]`
  - **Acceptance Criteria:** รูปแบบ `Given / When / Then` ทุกข้อ
  - **UI/UX Reference:** ลิงก์ Figma, Wireframe, Screenshot
- **การเปิดบน GitHub:** สามารถสั่งให้เปิด Issue ขึ้น GitHub Repository ได้ทันทีผ่าน `gh issue create`

### 2. การแตกใบงานใหญ่ (skill `split-issue`)
- นำ Issue ก้อนใหญ่ (Epic/Story/Backend API) มาแยกเป็นตั๋วงานขนาดพอดี:
  - `[FE] Develop: <ชื่องาน>`
  - `[BE] Develop: <ชื่องาน>`
  - `[Design] <ชื่องาน>` (ด่านตรวจดีไซน์: สำหรับ Story ที่เพิ่มหน้าจอใหม่แต่ยังไม่มีดีไซน์ใน Figma)
- ทุกข้อใน AC ต้องมีผู้รับผิดชอบ (ห้ามหลุด)
- ตรวจสอบความขัดแย้ง (Conflict) ของไฟล์และโมดูลระหว่าง Story ที่อาจทำพร้อมกัน

## Part 1 — First-round SDD (ทำครั้งเดียวเมื่อเริ่มโปรเจกต์)

เมื่อเริ่มต้นโปรเจกต์ใหม่ หรือเมื่อมีสถาปัตยกรรมใหม่ที่ไม่เคยกำหนดไว้:
1. Tech Lead ระบุข้อกำหนดสั้น ๆ เช่น:
   `[FE] Next.js 14 App Router · [BE] Go Gin · สถาปัตยกรรม Clean Architecture · DB PostgreSQL · Auth ด้วย JWT`
2. Agent `project-sdd-writer` ขยายความต้องการออกมาเป็น:
   - โครงสร้างโฟลเดอร์ของโปรเจกต์ทั้งหมด (Folder layout & Layer boundaries)
   - กฎการสร้างไฟล์ใหม่แต่ละประเภท
   - ชุดไฟล์ตัวอย่างเริ่มต้น (Starter example files)
   - รูปแบบ API มาตรฐาน และรูปแบบ Error Format ที่ทุก endpoint ต้องใช้ร่วมกัน
   - กฎการทดสอบ (Testing frameworks & commands)
   - Checklist การทำ Code Review และ Definition of Done (DoD)
3. Tech Lead ตรวจและอนุมัติ โดยบันทึกบรรทัดรับรอง:
   `Project SDD อนุมัติโดย: @<github-login> (<ชื่อ>) เมื่อ <วันที่>`

> 🛑 **หากยังไม่มี Project SDD หรือยังไม่ได้รับอนุมัติ → ห้ามเริ่ม Part 2 เด็ดขาด**

## Part 2 — ลูปการทำงานทีละ 1 ใบงาน (Per Ticket)

งานทุกอย่างของใบงานจะเก็บไว้ใน `docs/workspecs/<ISSUE-KEY>/` และบันทึกสถานะใน `_status.md`

### 🎨 ก่อนเริ่ม Stage A — การอ่านดีไซน์ (Design Input)
หากใบงานมีลิงก์ Figma หรือภาพแคปหน้าจอ:
- **AI ใน Main Session เป็นผู้อ่านดีไซน์เพียงครั้งเดียว** (ตามข้อกำหนดใน [`docs/design-source.md`](../../docs/design-source.md))
- เรียกใช้ `Framelink MCP for Figma` (`get_figma_data`, `download_figma_images`) หรือใช้ Multimodal Vision สแกนภาพแคปจอ
- บันทึกผลลัพธ์เป็น `docs/workspecs/<ISSUE-KEY>/design.md` และภาพลงโฟลเดอร์ `design/`
- Subagents ทุกตัวใน Stage A และ B จะอ่านข้อมูลดีไซน์จาก `design.md` โดยตรง

### Stage A — แตกใบงานเป็น Workspec รายฝั่ง (`workspec-writer`)
- ดึงข้อมูลจาก GitHub Issue (อ่าน Body, ทุก Comment, และ `design.md` หากมี)
- สร้าง `workspec-fe.md` และ `workspec-be.md`
- **กฎเหล็ก:** ทุก FR และทุก AC ต้องระบุเจ้าของ (`FE`, `BE`, หรือ `FE+BE`) ห้ามมีข้อตกหล่น
- หยุดรายงานผล และรอ Ticket Owner ยืนยัน

### Stage B — ทำสเปคให้เสร็จก่อนเขียนโค้ด (Multi-Agent)
Orchestrator สั่งรัน Subagents ร่วมกัน:
1. `codebase-scout`: สำรวจโค้ดเดิมและโมดูลที่มีอยู่ บันทึกเป็น `existing-inventory.md`
2. `spec-fe`: ระบุหน้าจอ, State, Widget, การผูกข้อมูล และ **ตาราง Design Tokens (Colors, Typography, Spacing, Assets)** บันทึกเป็น `spec-fe.md`
   - นำค่าสี (Hex), ฟอนต์, ระยะ Padding, และสถานะทั้ง 4 (`Loading`, `Empty`, `Error`, `Data`) จาก `design.md` มาแปลงเป็นสเปคทางเทคนิค
3. `spec-be`: ระบุ Endpoints, DTO, ตารางฐานข้อมูล, Business Rules บันทึกเป็น `spec-be.md`
4. `contract-checker` (จุดบรรจบ 1): เปรียบเทียบสัญญาสองฝั่ง (ชื่อฟิลด์, data type, nullability, error response) บันทึกเป็น `contract-report.md` (หากไม่ตรง ให้แก้ที่สเปค ห้ามแตะโค้ด!)
5. `test-author`: แปลงทุก AC ให้เป็นเคสทดสอบใน `testplan.md` โดยแบ่งประเภทชัดเจน:
   - 🤖 **Automated**: รันเทสด้วยโค้ด (TDD)
   - 👁️ **Review**: คนตรวจตอนดูโค้ดที่ Gate 7 (ความสะอาด, มาตรฐานชื่อ, ตรวจโค้ดเทียบ Design Tokens)
   - 🙋 **Manual QA**: ทดสอบด้วยมือที่ Stage D (ระบบชำระเงิน, ฮาร์ดแวร์, UX หน้าจอ)
6. รวมผลลัพธ์เป็น `spec.md` พร้อมบทสรุปสำหรับ Reviewer

### ✋ Gate 6 — ตรวจอนุมัติสเปค & แผนเทส (Tech Lead)
- Tech Lead ตรวจว่าสเปค Functional, API Contract, แผนการทดสอบ และ **Design Tokens (สี, ฟอนต์)** ครบถ้วนถูกต้องหรือไม่
- นี่คือจุดสุดท้ายที่สามารถเปลี่ยนการออกแบบได้โดยไม่ต้องรื้อโค้ด!

### Stage C — TDD (Test-Driven Development)
- พัฒนาทีละ AC ตามลูป:
  1. `test-author` เขียน Automated Test ที่ล้มเหลวก่อน (Red)
  2. `implementer` เขียนโค้ดแอปให้เทสผ่านพอดี (Green) โดยฝั่ง Frontend ให้นำ Design Tokens (Hex, Tailwind classes, Theme) จาก `spec-fe.md` ไปใช้โดยตรง
  3. `implementer` ปรับแต่งโค้ดให้สะอาด (Refactor) โดยที่เทสยังต้องผ่าน
- **กฎเหล็ก:** `implementer` ห้ามแก้ไฟล์เทสเด็ดขาด / `test-author` ห้ามแก้โค้ดแอป
- `test-reviewer` ตรวจสอบว่าทุก AC มีเทสคุมครบถ้วน (Test Coverage)
- ⋈ **จุดบรรจบ 2:** เชื่อมต่อทั้งระบบและรัน Integration / End-to-End Tests

### 🤖 AI Pre-review (ก่อนถึงตามนุษย์รอบแรก)
- รัน skill `code-review` ในโหมด `pre-review`
- แยกประเด็นเป็น 3 กลุ่ม:
  1. **AI แก้ได้เลย:** โค้ดผิดสไตล์, Dead code, จัดระเบียบเลเยอร์ → AI แก้ทันที
  2. **AI แก้ได้เลย · ต้องมีเทสก่อน:** พฤติกรรมที่สเปคกำหนดแต่ยังขาด → เขียนเทสก่อนแล้วแก้
  3. **ต้องให้คนตัดสิน:** จุดที่มีผลกระทบกับสเปคหรือดีไซน์ → ส่งต่อให้มนุษย์ที่ Gate 7
- วนลูปไม่เกิน 3 รอบ เพื่อให้เหลือภาระถึงคนน้อยที่สุด!

### ✋ Gate 7 — Code Review (Reviewer / Tech Lead)
- ตรวจสอบโค้ดบน Draft Pull Request หรือกิ่งงาน
- Reviewer ตรวจประเด็นที่เหลือจาก Pre-review และเคส 👁️ (รวมถึงความถูกต้องของ UI เทียบกับดีไซน์)
- เมื่อผ่านแล้ว Tech Lead ติ๊กอนุมัติ Gate 7

### Stage D — QA: งานแยกเป็น 2 กองบน Branch เดียวกัน
- **กอง Agent 🤖:** `test-reviewer` รันชุดการทดสอบทั้งหมด ยืนยันผลเป็นสีเขียว 100%
- **กองมนุษย์ 🙋:** Tester หรือ Ticket Owner ทดสอบเคสเฉพาะที่ไม่สามารถออโต้ได้ (เช่น เชื่อมโยงอุปกรณ์, สแกน QR, สัญญาณเน็ตหลุด)
- เมื่อผ่านทั้งสองกอง → ตั้งสถานะ PR เป็น **Ready for review** เพื่อให้ผู้มีสิทธิ์กด Merge เข้าสู่ Branch หลัก

## รูปแบบการหยุดรอคน (Stopping for People)

ทุกครั้งที่ AI สิ้นสุด Stage หรือหยุดรอการตัดสินใจของมนุษย์ ให้รายงานโดยขึ้นต้นด้วย:
> **👉 สิ่งที่คุณต้องทำตอนนี้:** [คำสั่งเดียวสั้นกระชับ เช่น "พิมพ์ว่า ไปต่อ", "กด Merge PR บน GitHub", หรือ "ตอบคำถาม 1-3"]
> ตามด้วย: สถานะปัจจุบัน และขั้นตอนถัดไปที่จะเกิดขึ้น
- แยกประเด็นเป็น 3 กลุ่ม:
  1. **AI แก้ได้เลย:** โค้ดผิดสไตล์, Dead code, จัดระเบียบเลเยอร์ → AI แก้ทันที
  2. **AI แก้ได้เลย · ต้องมีเทสก่อน:** พฤติกรรมที่สเปคกำหนดแต่ยังขาด → เขียนเทสก่อนแล้วแก้
  3. **ต้องให้คนตัดสิน:** จุดที่มีผลกระทบกับสเปคหรือดีไซน์ → ส่งต่อให้มนุษย์ที่ Gate 7
- วนลูปไม่เกิน 3 รอบ เพื่อให้เหลือภาระถึงคนน้อยที่สุด!

### ✋ Gate 7 — Code Review (Reviewer / Tech Lead)
- ตรวจสอบโค้ดบน Draft Pull Request หรือกิ่งงาน
- Reviewer ตรวจประเด็นที่เหลือจาก Pre-review และเคส 👁️
- เมื่อผ่านแล้ว Tech Lead ติ๊กอนุมัติ Gate 7

### Stage D — QA: งานแยกเป็น 2 กองบน Branch เดียวกัน
- **กอง Agent 🤖:** `test-reviewer` รันชุดการทดสอบทั้งหมด ยืนยันผลเป็นสีเขียว 100%
- **กองมนุษย์ 🙋:** Tester หรือ Ticket Owner ทดสอบเคสเฉพาะที่ไม่สามารถออโต้ได้ (เช่น เชื่อมโยงอุปกรณ์, สแกน QR, สัญญาณเน็ตหลุด)
- เมื่อผ่านทั้งสองกอง → ตั้งสถานะ PR เป็น **Ready for review** เพื่อให้ผู้มีสิทธิ์กด Merge เข้าสู่ Branch หลัก

## กฎเหล็ก 11 ข้อที่ AI ทุกตัวต้องยึดถือ (The 11 Hard Rules)

1. **อ่าน Project SDD ก่อนเริ่มเสมอ:** ทุกอย่างต้องอ้างอิงสถาปัตยกรรมและกฎของโปรเจกต์
2. **ทำหน้าที่ตามขั้นของตนเอง:** ห้ามข้ามขั้น หรือทำงานของ Agent ขั้นอื่น
3. **จบขั้นแล้วต้องหยุดรายงาน:** ห้ามไหลข้ามขั้นไปเองโดยไม่มีคำสั่ง "ไปต่อ"
4. **✋ ประตูมนุษย์เป็นของคนเท่านั้น:** AI ห้ามติ๊กเอง และห้ามสร้างบรรทัดอนุมัติเอง
5. **ความขัดแย้งในขั้นสเปคให้แก้ที่สเปค:** ห้ามแก้โค้ดเพื่อเอาใจสเปคที่ยังไม่นิ่ง
6. **คนเขียนเทส ≠ คนเขียนโค้ด:** `implementer` ห้ามแก้เทส, `test-author` ห้ามเขียนโค้ดแอป
7. **ยึดตาม Requirement ของ Story 100%:** ห้ามคิดฟังก์ชันเพิ่มเองตามอำเภอใจ
8. **ห้าม AI สั่ง Merge, Close PR, หรือ Delete Issue:** คำสั่งเหล่านี้เป็นสิทธิ์ของมนุษย์บน GitHub เท่านั้น
9. **ห้าม Push ตรงเข้า Main หรือ Master:** โค้ดทั้งหมดต้องแตก branch และผ่าน PR
10. **ลูปการตรวจซ่อมจำกัดสูงสุด 3 รอบ:** หากยังไม่ผ่าน ให้สรุปทางเลือกให้คนตัดสินใจ
11. **งานที่เจอนอกขอบเขตให้เปิดเป็น Issue รอ:** ห้ามแอบแก้ในใบงานปัจจุบัน ให้บันทึกเป็นงานรอ
